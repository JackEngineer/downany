# Downany · 百纳 Design System v1.0

- 状态：设计已确认，工程实现待开始
- 确认日期：2026-08-16
- 当前覆盖：Electron 桌面端、设置、历史、对话框、Toast、浏览器抓取窗口、Chrome 扩展、页内下载按钮、系统菜单、托盘、通知、安装、更新与 CLI
- 预留覆盖：官网及后续新增的用户可见载体
- 桌面端详细规则：[Desktop UI Profile](UI-DESIGN-LANGUAGE.md)
- 视觉基准：[主窗口强高斯玻璃原型](assets/downany-main-window-glass-v1.png)

> **外部安静，内部鲜活；操作克制，结果明确。**

> **媒体是内容，玻璃承载信息，窗口镀铬保持安静。**

本规范是 Downany 全产品最高层级的设计依据。它统一品牌气质、语义、组件、状态、交互模式和验收方式，但不要求所有载体套用相同皮肤。桌面窗口、浏览器扩展、系统通知和 CLI 必须保留各自媒介的合理表达。

## 1. 产品定位

Downany 是单一目的明确的专业下载工具。用户主要完成四件事：

1. 把媒体交给 Downany。
2. 判断任务当前状态。
3. 在失败时找到可执行的恢复路径。
4. 打开、传递或再次处理下载结果。

产品不应呈现为管理后台、内容平台或技术控制台。专业感来自命中率、结果质量、信息组织和行为可靠性，视觉材质只负责强化这些价值。

## 2. 设计系统架构

Downany 采用“统一基因，多种载体表达”的六层体系：

```text
品牌基因
  ↓
基础令牌
  ↓
通用组件
  ↓
业务模式
  ↓
载体配置
  ↓
具体产品界面
```

| 层级 | 负责内容 | 不负责内容 |
|---|---|---|
| 品牌基因 | 产品气质、注意力秩序、表达边界 | 单个页面布局 |
| 基础令牌 | 颜色、排版、间距、圆角、材质、动效 | 业务状态机 |
| 通用组件 | 按钮、输入框、菜单、对话框、反馈组件 | 特定下载流程 |
| 业务模式 | 添加、下载、恢复、历史、发送、更新 | 平台窗口外观 |
| 载体配置 | 媒体型、工具型、系统型、文本型表达 | 创造新的状态语义 |
| 产品界面 | 按真实场景组合前五层 | 绕过系统规则自定义视觉语言 |

## 3. 全系统不变量

以下规则适用于所有用户可见载体，Profile 和页面不得覆盖。

### 3.1 内容权重最高

- 媒体缩略图、文件、任务结果和可执行状态高于品牌装饰。
- 用户首先看到“下载什么”和“现在怎样”，随后才看到平台、格式和技术细节。
- 不以大面积品牌色、插画或玻璃效果掩盖真实内容。

### 3.2 操作层保持安静

- 窗口控制、产品名称和业务操作分层呈现。
- 常驻工具栏不使用大面积饱和按钮。
- 导航、筛选和工具操作不能同时争夺主视觉。

### 3.3 玻璃服务于阅读

- 玻璃用于建立内容与文字之间的可读对比，不用于填满空白。
- 强玻璃只出现在媒体内容复杂且确有阅读需求的区域。
- 设置、表单、菜单和普通列表默认使用实色或轻抬升表面。

### 3.4 一个区域只有一个主动强调

- 同一激活项不得同时使用高亮底、粗体、下划线和发光。
- 一个流程只有一个 `primary` 动作。
- 强调色面积应保持稀缺，把主要对比留给内容与当前决策。

### 3.5 状态不只依赖颜色

- 状态色只作为标记，不铺满整张卡片或整行。
- 进度、成功、暂停和失败必须同时有文字或图标。
- 不同载体必须保持相同的状态含义和结果文案。

## 4. 载体配置

### 4.1 四类 Profile

| Profile | 视觉特征 | 典型场景 |
|---|---|---|
| `media` 媒体型 | 影像主导、局部强阅读玻璃、克制操作 | 主任务横幅、媒体预览、官网产品演示 |
| `utility` 工具型 | 高密度、轻抬升表面、清晰分组 | 设置、历史、对话框、扩展弹窗 |
| `native` 系统型 | 遵循操作系统或宿主浏览器 | 菜单、托盘、通知、安装与更新 |
| `textual` 文本型 | 结构化文本、语义状态、无视觉材质 | CLI、诊断输出、非交互日志 |

### 4.2 可以变化的维度

- 玻璃、实色或系统原生材质。
- `compact` 或 `regular` 信息密度。
- 深色、浅色或跟随系统主题。
- macOS、Windows、Chrome 与终端的宿主行为。
- 动效、透明度和性能降级方式。

载体差异不得覆盖可访问性、状态语义、动作结果和错误恢复规则。

### 4.3 产品映射

| 产品触点 | 主要 Profile |
|---|---|
| 主窗口任务队列 | `media` |
| 历史、设置、对话框、Toast | `utility` |
| 浏览器抓取窗口 | `media + utility` |
| Chrome 扩展弹窗 | `utility`，附微型媒体预览 |
| 页内下载按钮 | `utility` 的轻量悬浮变体 |
| 系统菜单、托盘、通知 | `native` |
| DMG、NSIS 与系统安全提示 | `native` |
| 浏览器内安装引导与更新下载页 | `utility`，附有限品牌表达 |
| CLI 与诊断信息 | `textual` |
| 官网 | `media + utility`，仅在实际建设时启用 |

## 5. 材质系统

### 5.1 五级材质

| 层级 | 名称 | 用途 |
|---|---|---|
| M0 | `Canvas` | 窗口和页面底层 |
| M1 | `Raised Surface` | 设置、输入框、普通列表、常规控件 |
| M2 | `Soft Glass` | Popover、Toast、悬浮工具、页内按钮 |
| M3 | `Reading Glass` | 媒体横幅和大型媒体预览的文字区 |
| M4 | `Native Surface` | 系统菜单、托盘、通知和安装流程 |

### 5.2 Canvas

- 深色基准使用略带冷调的近黑色，不使用纯黑。
- 页面层级依靠细微明度差，不依靠大面积渐变。
- 大面积数字表面可以使用不超过 `1%` 的单色颗粒；颗粒不得影响截图、文字和媒体内容。

### 5.3 Raised Surface

- 与画布保持约 `4%–7%` 的克制明度差。
- 使用 `1px` 微弱内描边。
- 基础表面不使用常驻投影。
- 设置分组优先使用标题、间距和分隔线，不使用卡片墙。

### 5.4 Soft Glass

- 模糊建议 `20–24px`。
- 只用于悬浮在内容之上的小面积元素。
- 允许轻微内高光和柔和投影。
- 不与 `Reading Glass` 嵌套。

### 5.5 Reading Glass

`Reading Glass` 是 Downany 的标志性材质：

- 模糊 `32–40px`。
- 饱和度 `115%–125%`。
- 深色染色透明度根据缩略图亮度在 `0.32–0.48` 之间调整。
- 覆盖媒体横幅左侧约 `56%–60%`。
- 右侧使用 `80–110px` 羽化渐隐。
- 文字位于玻璃上层，不参与模糊。
- 原图只统一压暗约 `8%–10%`，不得失去辨识度。
- 每张可见媒体横幅最多使用一个大面积模糊层。

精确令牌与参考结构由 [Desktop UI Profile](UI-DESIGN-LANGUAGE.md#4-材质系统) 定义。

### 5.6 Native Surface

- 系统菜单、通知、托盘和安装过程优先使用宿主原生材质。
- Downany 只控制图标、命名、状态语义和文案。
- 不在原生载体中模拟自定义玻璃或 macOS 交通灯。

### 5.7 高级感控制

1. **强调色预算**：蓝色面积原则上不超过当前可见界面的 `5%`。
2. **圆角纪律**：只使用设计系统规定的有限档位，不把所有元素做成胶囊。
3. **阴影纪律**：只有真正悬浮的菜单、Toast 和对话框允许投影。
4. **边缘纪律**：玻璃依靠微弱描边、顶部内高光和渐隐建立边界，不使用白色亮边。
5. **对比纪律**：同层表面保持克制，把高对比留给内容、标题和当前操作。
6. **动效纪律**：只动画透明度、位移和描边，不动画模糊强度。

### 5.8 禁止的伪高级感

- 所有卡片都使用高斯模糊。
- 大面积蓝紫渐变、霓虹描边或外发光。
- 奶白半透明蒙版和厚重弥散阴影。
- 过亮边缘、过大圆角和卡片套卡片。
- 为展示材质牺牲信息密度。
- 在系统菜单和通知中模拟自定义玻璃。

## 6. 基础语言

### 6.1 令牌原则

- 令牌分为基础值与语义值。
- 组件只能引用语义令牌，不直接引用基础色。
- 语义命名描述用途，例如 `surface-raised`、`text-secondary` 和 `status-failure`，不描述偶然外观。
- 工程实现必须建立唯一、机器可读的语义 Token 源，再为 Electron、扩展和其他载体生成所需格式。
- 在唯一 Token 源落地前，现有样式只能视为迁移输入，不能视为全产品事实源。

语义 Token 至少覆盖：

```text
surface / text / stroke / accent / status
typography / spacing / radius / motion
material / focus / elevation / density
```

桌面端当前颜色值与旧令牌迁移关系见 [Desktop UI Profile](UI-DESIGN-LANGUAGE.md#3-设计令牌)。

### 6.2 产品界面排版

字体栈：

```css
-apple-system, BlinkMacSystemFont, "SF Pro Text", "PingFang SC",
"Hiragino Sans GB", "Segoe UI", "Microsoft YaHei UI", "Noto Sans SC",
sans-serif
```

| 角色 | 字号 / 行高 | 字重 |
|---|---:|---:|
| 辅助说明 | `11 / 16px` | `400` |
| 元信息 | `12 / 18px` | `400` |
| 控件与正文 | `13 / 18px` | `400–500` |
| 任务标题 | `15 / 21px` | `600` |
| 对话框标题 | `18 / 24px` | `600` |
| 页面标题 | `20 / 28px` | `600` |

- 产品界面常规文字禁止使用 `700`。
- 速度、大小、时间和进度使用等宽数字。
- CLI、路径和诊断信息使用系统等宽字体。
- 中文不增加字间距，英文品牌名保留原始大小写。
- 官网和安装引导可以使用 `24 / 32 / 40px` 展示字号，但展示字号不进入桌面工具界面。

### 6.3 间距与密度

基础间距只使用：

```text
2 / 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40px
```

- 布局以 `8px` 为主网格，`4px` 用于图标与文字等微间距。
- Downany 桌面端和扩展默认使用 `compact` 密度。
- 官网、安装引导和复杂选择流程可使用 `regular` 密度。
- 禁止引入没有语义的随机尺寸。

### 6.4 控件尺寸

| 元素 | 尺寸 |
|---|---:|
| 小型图标按钮 | `28px` |
| 常规控件 | `32px` |
| 官网或安装主按钮 | `40px` |
| 桌面标题栏 | `44px` |
| 桌面操作栏 | `48px` |
| 桌面筛选栏 | `36px` |
| 任务横幅 | `108px` |
| 紧凑任务横幅 | `96px` |

### 6.5 圆角

| 档位 | 值 | 典型用途 |
|---|---:|---|
| small | `6px` | 小标签、微控件 |
| control | `8px` | 输入框、按钮 |
| banner | `10px` | 媒体横幅 |
| popover | `12px` | 菜单、Toast |
| dialog | `14px` | 对话框 |

只有标签和真正的二元选择器允许胶囊圆角。

### 6.6 图标与品牌命名

- 常规图标使用 `16px`、约 `1.5px` 描边。
- 小型状态图标使用 `12px`。
- 同一操作在所有载体中使用同一图形语义。
- 禁止使用 Emoji、字体符号或不同风格图标混搭。
- 图标按钮必须有 Tooltip 和可访问名称。

品牌名称根据空间变化：

| 场景 | 名称 |
|---|---|
| 完整产品界面、关于、安装与官网 | `Downany · 百纳` |
| 扩展、托盘等紧凑载体 | `百纳` |
| 可执行文件、协议、包名与 CLI | `Downany` |

### 7.6 变体原则

组件变体只能表达真实语义：

```text
Button: primary / secondary / ghost / danger
Surface: canvas / raised / soft-glass / reading-glass
Density: compact / regular
Feedback: neutral / info / success / warning / danger
TaskState: pending / downloading / paused / completed / failed / cancelled
```

禁止创建 `blueButton2`、`specialCard`、`bigGlassPanel` 等页面专用视觉变体。

### 7.7 通用交互状态

每个可操作组件必须定义适用的交互状态；执行异步动作的组件还必须定义 `loading`：

```text
default → hover → pressed
        → focus-visible
        → disabled
        → loading
```

- Hover 只轻微提升填充或描边。
- Pressed 不做明显缩放。
- 键盘焦点统一使用 `2px` 焦点环。
- Loading 保留按钮宽度和动作名称。
- Disabled 不得因透明度过低而失去可读性。

## 8. 全产品业务模式

### 8.1 统一任务入口

```text
粘贴 / 拖放 / 扩展 / 网页识别 / Deep Link / .webloc / CLI
                                 ↓
接收链接 → 校验 → 解析 → 确认内容 → 加入队列 → 状态反馈
```

- 单条且结果明确时缩短流程。
- 多条链接、播放列表或格式选择进入确认面板。
- 重复任务明确提示，不静默添加。
- 解析失败提供网页识别、登录、更新工具或重试路径。
- 只有真正入队后才能显示“已加入下载”。

### 8.2 统一任务生命周期

```text
等待 → 下载中 → 已完成
  ├→ 已暂停 → 下载中
  ├→ 下载失败 → 重试
  └→ 已取消
```

| 状态 | 主要信息 | 首要操作 |
|---|---|---|
| 等待 | 队列位置、预计开始条件 | 取消 |
| 下载中 | 进度、速度、剩余时间 | 暂停 |
| 已暂停 | 当前进度 | 继续 |
| 已完成 | 文件大小、完成时间 | 打开 |
| 下载失败 | 用户可理解的原因 | 恢复操作 |
| 已取消 | 已停止 | 重新下载 |

桌面端、扩展、托盘和 CLI 必须使用同一状态含义。

### 8.3 失败恢复合同

每条错误必须包含三个层次：

```text
发生了什么 → 为什么 → 现在可以做什么
```

统一用户错误类别：

- 需要登录。
- 网络连接失败。
- 地区不可用。
- 视频已删除或设为私密。
- 没有可用格式。
- 磁盘空间不足。
- 下载工具需要更新。
- 桌面端未连接。
- Telegram 发送失败。
- 未知错误。

普通界面不显示异常栈、Sidecar、yt-dlp 参数或内部路径。CLI 只有在详细模式下才展示技术信息。

### 8.4 反馈优先级

1. **行内状态**：任务自身的进度、失败和恢复。
2. **Toast**：一次操作的结果。
3. **对话框**：破坏性操作或复杂选择。
4. **系统通知**：用户切出应用后仍需知道的完成或失败结果。

禁止使用 Toast 持续播报进度，也不能为普通成功操作频繁发送系统通知。

### 8.5 历史模式

- 历史只回答下载过什么、文件在哪里、能否再次下载。
- 首要操作为 `打开` 或 `重新下载`。
- 搜索覆盖标题、平台和文件名。
- 删除单条记录优先允许撤销；清空历史必须确认。
- 删除历史不等于删除本地文件，文案必须明确区分。

### 8.6 浏览器扩展连接模式

```text
检测媒体 → 选择媒体 → 正在发送 → 已加入队列
                             ├→ 桌面端未运行
                             └→ 发送失败
```

- `已加入队列` 不能写成“下载完成”。
- 桌面端未运行时提供打开百纳、重新检测和安装入口。
- 页内按钮只负责快速入队，详细进度留在扩展弹窗或桌面端。
- 最近任务与桌面端保持相同状态和进度含义。

### 8.7 Telegram 双状态模式

```text
下载：等待 / 下载中 / 已完成 / 失败
发送：未启用 / 等待发送 / 发送中 / 已发送 / 发送失败
```

- Telegram 发送失败不得把已完成的下载任务改成下载失败。
- 发送失败提供 `重新发送` 和 `检查 Telegram 设置`。
- 设置页不暴露凭证。
- Toast 和系统通知明确区分“下载完成”与“已发送到 Telegram”。

### 8.8 安装与更新模式

```text
正在检查 → 已是最新
         → 发现新版本 → 前往下载
         → 检查失败 → 重试
```

- 当前只支持前往下载时，不得使用“自动更新中”等文案。
- 安装、SmartScreen 和 Gatekeeper 指引采用平台原生结构。
- 开发命令、内部端口和占位网址不得出现在正式用户界面。

### 8.9 空状态与首启

空状态只保留一个主要动作：

| 场景 | 核心表达 |
|---|---|
| 主队列 | `粘贴视频链接` |
| 历史 | `还没有下载记录` |
| 扩展 | `播放视频后重新检测` |
| 抓取窗口 | `打开需要识别的视频页面` |
| Telegram | `连接 Telegram` |

不使用大面积插画、营销口号或多个同级按钮填充空白。

## 9. 产品载体规范

### 9.1 桌面主窗口

```text
WindowChrome
ActionBar
FilterBar
TaskViewport
```

- `WindowChrome` 只包含窗口控制与产品名。
- `ActionBar` 承载链接、添加、网页识别、搜索和设置。
- `FilterBar` 承载任务状态筛选。
- `TaskViewport` 以媒体横幅为主体。
- 背景、操作栏和筛选栏保持安静，强玻璃只出现在媒体横幅文字区。

更详细的窗口尺寸、状态和组件规则见 [Desktop UI Profile](UI-DESIGN-LANGUAGE.md)。

### 9.2 设置窗口

- 导航与内容区清晰分离。
- 分组依靠标题、间距和分隔线，不使用卡片墙。
- 开关、选择器和输入框使用 `Raised Surface`。
- Telegram、代理和下载目录等复杂区域可以使用独立子面板，但不得层层嵌套。
- 保存结果使用行内状态或 Toast。

### 9.3 历史与下载记录

- 使用 `MediaTaskBanner compact` 或语义一致的紧凑记录行。
- 批量选择时显示上下文工具栏，不常驻大量批量按钮。
- 文件不存在时提示“文件已移动或删除”，并提供重新下载。
- 不使用强玻璃作为装饰背景。

### 9.4 添加确认与播放列表

- 普通添加确认使用中型对话框。
- 播放列表、合集和多格式选择使用宽面板。
- 顶部显示来源与媒体摘要，中部选择条目，底部固定操作区。
- 选中状态只使用轻底色、勾选和数量反馈。
- 不把每一项做成独立厚重卡片。

### 9.5 浏览器抓取窗口

```text
地址与操作栏
嵌入浏览器
媒体候选面板
状态与加入操作
```

- 浏览器内容保持原样，不叠加产品滤镜。
- 媒体候选使用紧凑列表。
- 选中项可以显示较大的媒体预览，并局部使用 `Reading Glass`。
- URL、格式和来源属于次级信息。
- 主操作始终是 `加入下载`。

### 9.6 Chrome 扩展弹窗

- 建议宽度保持约 `360px`。
- 顶部显示当前页面摘要与媒体数量。
- 中部为可选择媒体列表。
- 底部只保留一个主要动作。
- 最近任务位于次级区域，不与当前媒体争夺注意力。
- 不复刻桌面大横幅，最多使用微型媒体预览。
- 控件高度使用 `28–32px`，不使用移动端式大按钮。

### 9.7 页内下载按钮

- 使用小面积 `Soft Glass`。
- 由下载图标和简短文字组成。
- 默认安静，Hover 后提高对比。
- 状态只包括下载、正在发送、已加入和无法连接。
- 成功与失败状态短暂展示后恢复。
- 不使用鲜艳实心蓝胶囊长期覆盖网页内容。

### 9.8 系统菜单、托盘与通知

- 使用平台原生字体、尺寸、选中行为和布局。
- 托盘菜单只显示总体状态、关键任务和常用动作。
- 通知标题表达结果，正文补充对象，动作提供下一步。
- 不复刻玻璃、媒体横幅或自定义按钮。
- macOS 与 Windows 可以外观不同，但状态名称必须一致。

### 9.9 安装与更新

- DMG、NSIS 和系统安全提示遵循操作系统原生结构。
- 浏览器内安装引导与更新下载页使用 `utility` Profile，并附有限品牌表达。
- 品牌页面采用简洁实色背景，最多允许一处媒体或玻璃视觉。
- 主操作明确使用下载、安装、重新检测或前往更新。
- Gatekeeper 与 SmartScreen 指引独立呈现，不混入普通更新提示。

### 9.10 CLI 与诊断

```text
✓ 已加入 1 个任务
→ 下载中  58%  12.4 MB/s  剩余 01:24
✓ 已完成  /Downloads/video.mp4
! 下载失败  页面需要登录
  建议：使用百纳的网页识别功能
```

- 非交互输出不依赖颜色。
- 普通模式只显示结果和恢复建议。
- 详细模式才显示错误码与技术信息。
- 日志与用户输出严格分离。

### 9.11 官网

官网尚不是当前仓库的已交付界面；建设时必须遵循以下规则：

- 首屏展示产品能力和真实界面，不使用抽象渐变球。
- 全页最多设置一处主要 `Reading Glass` 场景。
- 下载按钮根据操作系统给出明确版本。
- 功能说明优先表达用户能完成什么，不展示内部架构。
- 官网可以更舒展，但颜色、图标、状态和圆角仍继承本系统。

## 10. 跨平台、可访问性与性能

### 10.1 macOS

- 桌面窗口可使用 `hiddenInset` 与系统 Vibrancy。
- 左侧保留交通灯和拖动空间。
- 使用原生菜单、快捷键和右键菜单行为。

### 10.2 Windows

- 使用系统窗口框架和窗口按钮。
- 不模拟 macOS 交通灯。
- 内部操作栏、任务横幅和状态语义与 macOS 保持一致。
- 没有系统 Vibrancy 时使用语义表面色，不以强阴影补偿。

### 10.3 可访问性

- 正文和控件文字达到 WCAG AA `4.5:1`。
- 大文字和非文字控件至少达到 `3:1`。
- 所有键盘操作元素使用一致的 `2px` 焦点环。
- 桌面点击目标最小 `28px`，常规目标建议 `32px`。
- 进度、成功和失败不能只依赖颜色。
- `prefers-reduced-transparency` 或不支持模糊时，玻璃退化为高不透明实色表面。
- `prefers-reduced-motion` 时关闭非必要位移与缩放。
- 200% 缩放后主要操作必须保持可用。

### 10.4 性能

- 每张可见横幅只允许一个大面积高斯玻璃层。
- 禁止嵌套大面积 `backdrop-filter`。
- 长列表只渲染或计算可见内容。
- 不在滚动过程中持续分析缩略图亮度。
- 不动画 `backdrop-filter`。
- 无模糊降级不得改变布局或操作顺序。

## 11. 设计系统治理

### 11.1 事实源优先级

发生冲突时按以下顺序处理：

1. 已有产品行为、安全边界和可访问性要求。
2. 本文的全产品原则、语义与业务模式。
3. 具体载体 Profile 的尺寸、材质和组件规则。
4. 组件实现与页面组合。
5. 视觉原型的气质与构图。

原型不是功能规格。实现不得为了像素模仿而删除暂停、继续、失败恢复、历史、批量操作、键盘、右键菜单或 Telegram 状态能力。

### 11.2 工程归属

工程落地后必须形成：

```text
唯一语义 Token 源
→ 通用 UI 组件
→ Downany 业务组件
→ 各载体页面
```

- Electron 与浏览器扩展从同一 Token 源生成各自格式。
- 通用组件与下载业务组件分开维护。
- 页面只能组合组件，不重新发明按钮、状态和玻璃规则。
- 不在多个载体中手动维护近似但不同的颜色和尺寸。

### 11.3 组件成熟度

| 状态 | 含义 |
|---|---|
| `draft` | 规则仍在探索 |
| `experimental` | 已使用，但接口可能调整 |
| `stable` | 通过适用载体的复用与验收 |
| `deprecated` | 进入迁移期，不再新增使用 |

组件通过深浅主题、键盘、降级和视觉验收后才能进入 `stable`。

### 11.4 版本策略

- `1.x` 增加组件和载体规则，不破坏现有语义。
- `2.0` 表示核心 Token、交互语义或品牌方向发生不兼容变化。
- 视觉参数调整必须记录原因和影响范围。
- 页面不得修改全局 Token 来解决局部问题。

### 11.5 变更流程

```text
发现问题
→ 判断局部问题或系统问题
→ 更新规范或组件
→ 制作真实场景原型
→ 验证完整状态
→ 迁移现有界面
→ 删除旧实现
```

确需例外时必须记录原因、适用载体、作用范围和回收条件，且不得扩散到其他页面。

## 12. 验收体系

### 12.1 视觉验收

- 与已确认原型保持相同气质、材质边界和注意力层级。
- 不追求逐像素复制生成图。
- 检查推荐尺寸、最小窗口和高缩放显示。

### 12.2 状态验收

每个组件至少检查：

```text
默认 / Hover / Pressed / Focus
禁用 / Loading / 空状态 / 错误状态
```

任务组件必须覆盖等待、下载中、暂停、完成、失败和取消。

### 12.3 主题与平台验收

- 深色、浅色和跟随系统。
- macOS 与 Windows 窗口控制区。
- Chrome 扩展 `360 × 520px`。
- 无透明、无模糊和减少动效模式。

### 12.4 验收证据边界

以下结果必须分别报告，不能互相替代：

- 自动化测试通过。
- 项目已配置的 TypeScript、静态检查与构建通过。
- 浏览器视觉检查通过。
- macOS 实机检查通过。
- Windows 实机检查通过。
- 用户视觉确认通过。

构建成功不代表视觉达到要求；原型满意也不代表业务行为没有回归。

## 13. 增量迁移顺序

1. 建立唯一语义 Token 源及各载体输出。
2. 固化按钮、输入框、图标、状态和焦点组件。
3. 重构窗口标题层、操作栏和筛选栏。
4. 将任务卡片迁移为 `MediaTaskBanner`。
5. 迁移历史、设置、Toast、对话框与空状态。
6. 迁移浏览器抓取窗口。
7. 统一 Chrome 扩展与页内下载按钮。
8. 统一托盘、通知、安装和更新文案。
9. 统一 CLI 用户输出。
10. 官网出现时直接消费同一品牌和 Token 体系。

迁移必须增量进行。每个阶段保留现有业务行为，不进行一次性全界面重写。

## 14. 完成定义

只有同时满足以下条件，才能称为“整个系统的设计语言已经落地”：

- 总纲覆盖全部用户触点。
- 语义 Token 已成为唯一工程事实源。
- 核心组件在适用载体中复用。
- 状态、反馈和错误恢复模式保持一致。
- 桌面端与扩展通过视觉回归。
- macOS、Windows 和降级模式通过检查。
- 新界面可以从现有规则中完成设计，不需要重新发明视觉语言。

当前仓库只完成了设计方向和正式规范确认，尚不能据此声称工程设计系统已经落地。
