# Downany v0.2.2 → v0.3.0 分阶段升级设计

- 日期：2026-08-26
- 状态：设计已形成，等待用户确认
- 产品范围：Downany · 百纳 Electron 桌面端、Python Sidecar、Chrome 扩展、官网与发布链路
- 当前公开基线：`v0.2.1`
- 目标版本：`v0.3.0`

## 1. 决策

采用“按用户链路逐级收口”的升级方式，不直接把当前版本一次性改成 `0.3.0`，也不按旧路线图的模块编号机械推进。

每个中间版本只承担一个可向用户说明、可独立验收的结果：

1. `v0.2.2`：用户能够找到安装包并完成首次使用。
2. `v0.2.3`：常见下载失败能够得到正确原因和可执行的恢复动作。
3. `v0.2.4`：播放列表、字幕、封面、元数据和落盘结果正确可用。
4. `v0.2.5`：长时间队列、暂停续传、崩溃恢复和批量操作稳定。
5. `v0.3.0`：以上能力在 macOS 与 Windows 上形成完整、可升级、可诊断的公开稳定基线。

任何版本都不能只以版本号、自动化测试或成功构建作为完成依据。完成必须有与该版本用户结果相匹配的可见运行验收。

## 2. 当前事实基线

### 2.1 已确认的发布状态

- `v0.2.1` 已公开发布。
- Release 同时包含 macOS Apple Silicon DMG、Windows x64 NSIS 安装包和 Chrome 扩展 ZIP。
- 当前安装包未签名；应用内更新为检查 GitHub Release 后引导用户手动下载安装。
- 当前代码版本为桌面端/Sidecar `0.2.1`，扩展 `0.8.2`。

### 2.2 已存在、不得重复开发的能力

旧 `docs/roadmap.md` 写于 2026-08-01，部分差距描述已经失效。当前代码已经包含：

- 内置网页识别窗口和独立持久会话。
- 浏览器 Cookie 导入与扩展传入 Cookie。
- `need_login`、`geo_blocked`、`ytdlp_outdated` 等结构化错误码。
- 下载失败后的网页识别、更新 yt-dlp 等操作入口。
- 播放列表解析、选集、分组、分组目录和队列持久化。
- 封面、元数据、章节嵌入。
- 分片并发设置。
- 队列重排协议与持久化。
- 诊断包导出。
- GitHub Release 更新检查。
- 中英文文案基础设施的初步接入。

这些能力在后续版本中的任务是验证、补齐和修复真实链路，不是重新实现同名功能。

### 2.3 当前明确缺口

- Chrome 扩展检测不到桌面端时，安装引导仍指向未上线的 `https://downany.app/download`。
- 扩展安装页仍显示“占位、上线后即可用”等内部状态文案。
- 本地官网代码已经能够解析 GitHub Release 资产，但尚未形成公开可访问的官网交付；本计划不擅自部署或绑定域名。
- 旧路线图无法反映当前代码事实，继续照表执行会重复开发。
- 自动化测试覆盖大量组件与协议，但还不能证明登录墙、真实 HLS、真实播放列表、长队列恢复和双平台安装链路全部可用。
- 公开仓库当前没有开放 Issue，不能把“没有反馈”解释为“没有缺陷”。

## 3. 方案比较

### 方案 A：按用户链路逐级收口（采用）

从获取安装包开始，依次收口首次使用、失败恢复、成品质量、队列耐久性，最后形成 `v0.3.0`。每一版都能独立发布，也能在发现高优先级缺陷时插入补丁版本。

优点：用户结果清楚，风险被分散，版本是否完成容易验真。缺点：需要维护跨版本回归矩阵，并持续更新文档事实。

### 方案 B：按技术模块推进

依次完成 Renderer、Sidecar、下载核心、扩展和发布脚本，再集中联调。

优点：工程边界整齐。缺点：单个版本可能没有完整用户结果；旧路线图已经与代码漂移，容易重复开发或留下跨模块断点。

### 方案 C：直接建设 `v0.3.0`

建立长寿命里程碑分支，把所有改动完成后一次发布。

优点：版本叙事简单。缺点：集成风险集中、验证周期过长、`main` 与真实发布基线长期分离，不符合仓库的短分支约定。

## 4. 版本阶梯

### 4.1 v0.2.2 — 安装与首次使用可靠

#### 用户结果

用户从扩展、README、官网本地构建或 GitHub 页面进入时，都能到达真实存在的安装包；安装后能够启动应用、加入一条公开链接、看到结果，并在失败时导出诊断包。

#### 范围

- 修复扩展安装引导的失效下载地址。
- 将扩展内下载地址集中为一个事实源，默认回退到 GitHub `releases/latest`。
- 删除用户界面中的“占位、开发联调、上线后”等内部文案。
- 核对 README、扩展说明、设置页更新说明和 Release 文档的入口一致性。
- 建立首次使用验收脚本或清单，覆盖安装、启动、扩展桥、公开链接入队、诊断导出和卸载。
- 更新 `docs/roadmap.md` 的当前能力与缺口，不改变尚未验证能力的事实状态。

#### 发布门槛

- Windows 干净目录或干净测试用户下完成安装、启动、公开链接入队、退出和卸载。
- macOS CI 包内冒烟继续通过；公开发布前还必须补一台真实 macOS 的可见安装与启动验收。
- 扩展在桌面端未安装、未运行、已运行三种状态下都给出正确下一步。
- 所有下载入口最终指向存在的 Release 页面或真实资产，不出现死链。
- Python、Electron、扩展测试与生产构建通过。

### 4.2 v0.2.3 — 下载失败可自救

#### 用户结果

下载失败时，用户知道发生了什么，并能直接执行最可能有效的恢复动作；不需要理解 yt-dlp、Cookie 文件格式或内部协议。

#### 范围

- 建立真实回归 URL 分类：公开直链、登录后页面、纯 HLS/MPD、已删除内容、地区限制、过期 yt-dlp、临时网络失败。
- 核对错误分类从下载核心、Sidecar 快照到 Renderer 文案的一致性。
- 验证 `need_login` 的 Cookie 导入和网页识别路径。
- 验证 `ytdlp_outdated` 的检查、更新和重试路径。
- 验证网络/代理错误不会被误报为不支持站点。
- 对可能已经成功但回执不确定的操作禁止盲目重复，避免重复下载或重复发送。

#### 发布门槛

- 回归矩阵中的每个样本要么成功下载，要么得到正确分类和可执行动作。
- 每个恢复动作至少有自动化合同测试和一次真实可见操作证据。
- 原始异常、Cookie、Token、本地路径和响应正文不得出现在普通用户界面。

### 4.3 v0.2.4 — 成品正确可用

#### 用户结果

用户下载单条内容或播放列表后，得到的文件名称、目录、字幕、封面、元数据和章节符合设置，能够直接在系统文件管理器或常见播放器中使用。

#### 范围

- 验证 YouTube 播放列表、Bilibili 多 P/合集及至少一个普通站点列表。
- 收口选集、分组折叠、分组删除和重启后分组恢复。
- 明确字幕语言、自动字幕、独立字幕与嵌入字幕的产品语义。
- 验证封面、标题、章节和媒体容器的兼容组合。
- 收口非法字符、超长路径、重名和播放列表子目录规则。
- 仅在真实需求证明后扩展后处理管线，不在本版本引入无验证价值的新处理步骤。

#### 发布门槛

- 每个目标平台至少有一个真实样本完成“解析 → 选择 → 下载 → 打开文件”验收。
- 重启应用后，播放列表分组和任务状态保持正确。
- 成品通过 ffprobe/文件存在性检查，并在至少一个系统播放器中可见打开。

### 4.4 v0.2.5 — 队列与恢复稳定

#### 用户结果

用户可以让应用长时间运行并处理多任务；暂停、退出、崩溃或网络中断后，不会丢队列、重复完成任务或破坏已下载文件。

#### 范围

- 队列重排、分组与优先级持久化。
- 暂停、继续、取消、失败重试和整组操作的状态机一致性。
- Sidecar 异常退出、Electron 重启和系统重启后的恢复。
- 分片并发、任务并发和限速组合下的资源使用与进度准确性。
- 大队列下 Renderer 更新频率、SQLite 写入和日志体积控制。
- Telegram 发送状态继续与下载完成状态解耦，发送失败不得回写为下载失败。

#### 发布门槛

- 建立固定的多任务恢复场景并重复运行。
- 所有任务 ID、分组、顺序和最终文件在恢复前后保持可解释的一致性。
- 不出现重复下载、完成文件被删除、暂停任务自动完成或失败任务无限重试。

### 4.5 v0.3.0 — 完整稳定公测基线

#### 用户结果

新用户能够完成获取、安装、首次下载、复杂页面恢复、播放列表下载和诊断；现有用户能够从 `v0.2.1` 或最近一个 `v0.2.x` 版本升级，并保留设置、队列和历史。

#### 范围

- 合并 `v0.2.2` 至 `v0.2.5` 的回归矩阵，删除重复或失效的测试入口。
- 验证 `v0.2.1 → v0.3.0` 和最近版本到 `v0.3.0` 的数据迁移。
- 完成中英文关键用户路径文案一致性，不要求一次性翻译全部低频界面。
- 统一 README、路线图、发布说明、扩展说明和官网能力事实。
- 生成同一版本的 DMG、NSIS 与 Chrome 扩展 ZIP，并验证版本、大小和 SHA256。
- 签名与自动替换更新只有在证书和授权可用时进入范围；没有证书时继续使用明确的系统安全提示和手动更新。

#### 发布门槛

- Windows 与 macOS 的真实可见核心链路验收通过。
- 从旧版本升级后，设置、队列、历史和 Telegram 配置满足迁移合同。
- 固定真实 URL 回归集无阻断级缺陷；所有预期失败都有正确的用户动作。
- 三件发布物属于同一源码版本，Release 非草稿、非预发布，公开 URL 可访问。
- 发布仍需用户明确授权；设计、实现和本地候选成功不自动授权推送、打标签或公开发布。

## 5. 跨版本架构约束

### 5.1 单一产品主线

继续使用 Electron Main + preload IPC + React Renderer + Python Sidecar + yt-dlp。不得重新引入 PyQt、SwiftUI 或第二套下载主线。

### 5.2 协议与数据

- Renderer 只通过 preload 暴露的有限 IPC 调用 Main。
- Sidecar stdout 只写 JSON Lines 协议；日志写 stderr 或日志文件。
- 协议新增字段必须向后兼容；TypeScript union/enum 使用 exhaustive `never`。
- SQLite 和 JSON 设置变更必须有旧数据迁移或稳定默认值。
- 下载完成与 Telegram 发送完成是两个独立结果。

### 5.3 错误与隐私

- 用户界面展示稳定错误类型、对象、动作和结果，不展示内部链路。
- Cookie、Token、Telegram 凭据、本地绝对路径和未脱敏响应不得进入界面、公开日志、提交或诊断包。
- 诊断包必须在本机生成，并明确告诉用户保存位置和包含内容。

### 5.4 发布纪律

- `main` 始终保持可发布，不建立长寿命 `v0.3.0` 分支。
- 一个独立增量使用一个短分支和可审查提交。
- DMG、NSIS 与扩展 ZIP 同版本发布；Windows-only 或 macOS-only 构建只是候选，不是正式版本。
- 未经用户明确授权，不合并、不推送、不创建 tag、不发布 Release。

## 6. 测试与证据模型

每个版本使用四层证据，不能互相替代：

1. **合同测试**：纯函数、协议、持久化迁移和组件行为。
2. **生产构建测试**：Electron build、Sidecar 打包、扩展 ZIP 和安装包结构。
3. **可见运行验收**：真实窗口、真实安装路径、真实任务和真实结果文件。
4. **公开交付验证**：Release 状态、三件资产、版本、大小、SHA256、旧客户端发现新版。

版本候选至少记录：

- 源码提交 SHA。
- 桌面端、Sidecar 与扩展版本。
- 自动化测试命令与结果。
- 安装包名称、大小与 SHA256。
- Windows/macOS 可见验收结果及未完成边界。
- 是否推送、打标签和发布的明确状态。

## 7. 第一个实施子项目：v0.2.2 下载入口闭环

### 7.1 问题

Chrome 扩展在未检测到桌面端时会打开安装引导，但引导页、后台回退和 README 当前使用未上线的 `https://downany.app/download`。用户无法从该路径获得安装包，且页面显示内部占位文案。

### 7.2 设计

- 新建扩展侧下载入口事实源，值为 `https://github.com/JackEngineer/downany/releases/latest`。
- `background.js` 和 `install.js` 共同使用该事实源，避免同一 URL 多处漂移。
- `install.html` 的静态无脚本回退同样指向 GitHub Releases。
- 页面主操作使用用户语言：`下载 Downany`。
- 辅助说明只告诉用户“安装并启动一次后再回到网页重试”，不显示开发命令、上线状态或实现细节。
- README 将该路径描述为正式安装回退，不再称为占位入口。
- 暂不部署官网；官网部署是需要独立授权和外部环境验证的后续增量。

### 7.3 失败处理

- 扩展内安装页打开失败时，直接打开 GitHub Releases。
- 创建标签页失败时，返回稳定失败结果，由现有扩展提示展示可理解的重试建议。
- 桌面端只是未运行时，仍先尝试 `downany://open` 并等待桥恢复；不能立即误导用户重新安装。

### 7.4 测试

- 下载入口常量合同测试。
- 安装页静态链接与脚本链接一致性测试。
- 桥在线、离线后唤起成功、未安装三种路径测试。
- 扩展现有 `shared.test.js`、`sniff-core.test.js` 和相关后台测试通过。
- 扩展 ZIP 中存在安装页及其依赖，且不包含测试文件。

### 7.5 完成定义

- 扩展任何安装回退都能到达当前公开 Release。
- 用户可见安装页不含占位或开发流程文案。
- 自动化合同与扩展构建验证通过。
- 变更形成独立本地提交；不推送、不发布。

## 8. 明确不做

- Linux 客户端。
- DRM 绕过或自研下载引擎。
- 为追求版本号重写现有稳定架构。
- 在 `v0.3.0` 前启动付费、账户、许可或远程内容托管。
- 未取得证书时伪装成已签名或承诺自动替换更新。
- 未经授权部署官网、绑定域名、推送代码、创建 tag 或公开 Release。

## 9. 设计完成定义

- 版本阶梯中的每一版都有唯一用户结果、明确范围和可验证发布门槛。
- 已存在能力与真实缺口分开记录。
- `v0.3.0` 的完成标准覆盖获取、安装、下载、恢复、成品、队列、升级、诊断和双平台交付。
- 第一个 `v0.2.2` 子项目足够独立，可以进入实施计划。
- 文档不含未决占位，外部凭据、签名和公开发布均有明确授权边界。
